# N3.1 Stock Photo — plan

One optional photo per stock item. Proposed, not built: nothing in this
document has been implemented, no dependency has been added, and no Firebase
project has been touched.

N3.1 sits on top of N3, which is **open** — single-device staging verification
passed, physical two-device concurrency verification pending
(`docs/N3-verification.md`). N3.1 must not change any settled N3 behaviour:
quantity, archive and permissions all stay exactly as they are.

## The user flow

**Adding a photo.** A stock card with no photo shows a small camera affordance
to anyone who may manage photos. Tapping it opens a sheet offering **Take a
photo** and **Choose from gallery** — the same two-mode shape Add stock uses,
because the first pass proved a single crowded sheet is the thing people get
wrong. Either route lands on a **preview**: the picture, an **Add photo**
button and **Cancel**. Nothing is uploaded until Add photo is pressed.

**Looking at one.** A card with a photo shows a thumbnail. Tapping it opens a
larger view. A Worker gets the thumbnail and the larger view and nothing else.

**Replacing or removing.** The larger view carries **Replace** and **Remove**
for anyone who may manage photos. Replace re-enters the same two-mode sheet.
Remove asks once, then clears it.

**Offline.** Every one of those controls is disabled offline, with the same
wording the stock controls already use. A photo already on the device stays
viewable.

## Proposed defaults

These are the Owner's, restated with the mechanism each one implies.

| Default | How it is met |
|---|---|
| One optional photo per stock item, catalogue and manual alike | A single `photoPath` string on the `/stock` document. No photo is the empty string, which is how every other optional string on that document already reads |
| Camera and gallery, preview, confirm, cancel | `TakePicture` and `PickVisualMedia`, then a preview panel whose confirm is the only thing that uploads |
| Thumbnail on the card, tap for a larger view | A ~44dp thumbnail in the card's title row; the larger view is a bounded panel in a dialog, like History |
| Owner/Admin/Staff add, replace, remove; active Workers view | `canManageStockPhoto = canAdjustStock`; `canViewStockPhoto = canViewStock`. Enforced in `Permissions`, in the Firestore rules and in the Storage rules |
| Changes need connectivity; cached photos stay viewable offline | The existing `requireOnline()` guard, plus an image cache keyed on the storage path |
| Compress and fix orientation before upload | Decode bounded, rotate by EXIF, re-encode JPEG. The arithmetic is pure and unit-tested; only the bitmap I/O touches Android |
| A failed upload or replacement preserves the existing photo | Upload to a **new** object, then swap the pointer in a transaction, then delete the old one. Nothing destructive happens before the new object exists |
| Immutable stock identity | The path is built from `StockRecord.key` via `Keys.stockDocId`, never from a display model |
| Photo changes stay out of quantity movements | `lastAction: "photo"` on the stock document and **no `/stockMoves` write**, exactly as a note-only save already behaves |
| Simultaneous replacement and cleanup are safe | The swap transaction returns the path it displaced; the caller deletes that one. Two racing replacements leave one live object and delete the other |
| Quantity, archive and permission behaviour preserved | The photo write re-asserts the stored `q` and `min` inside the same transaction shape N3 already uses, and touches nothing else |

## What the architecture already gives

Repository findings, checked in this tree at `92f2cf1`:

- **`ProductRecord.stockKey` / `Keys.stockDocId` already exist** and are the
  settled immutable identity. `stockDocId` is the logical key with `/`
  replaced by `_`, so `gateMotors|SIE1000` → `gateMotors|SIE1000` and a manual
  item is `manualstock|<slug>`. Both are safe as a path segment.
- **`StockStore` / `StockTransaction` is a testable seam** over the Firestore
  transaction, built precisely so a retry can be driven by a test. A photo
  swap is another planner function through it — no new data layer.
- **`StockWrite.stockFields()` already re-asserts `q`, `min`, `t`,
  `lastAction`, `by`, `byUid` and `serverAt` on every write.** The `/stock`
  update rule *requires* `q`, `min` and `t` on every update, so a photo-only
  write has to carry them. It gets that for free.
- **A note-only save already writes no movement.** Photo changes copy that
  decision rather than inventing one.
- **`FileProvider` is already declared** with authority
  `${applicationId}.files` and an `@xml/file_paths` config. Camera capture
  needs one `<cache-path>` entry added — not a new provider.
- **Coil 3 is already a dependency** (`io.coil-kt.coil3:coil-compose:3.2.0`)
  and is currently **unused in `app/src/main`**. The APK already carries it.
- **No `CAMERA` permission is declared, and none should be.** `TakePicture`
  delegates to the camera app, and `PickVisualMedia` is the system photo
  picker. Declaring `CAMERA` would make it a runtime permission this feature
  then has to request; not declaring it keeps the flow permission-free.
- **What is missing:** no `firebase-storage` dependency, and
  `firestore/firebase.json` declares only `firestore.rules` and
  `firestore.indexes.json` — there is **no `storage` block and no storage
  rules file**, so storage rules cannot be deployed or emulated until both are
  added.

## Data model

### On the `/stock` document

One new field. Additive, like `name` before it.

| Field | Type | Meaning |
|---|---|---|
| `photoPath` | string | The storage object path. Empty or absent means no photo |

Blank-means-absent is deliberate: `StockStore.resolve()` drops nulls rather
than writing them, so removing a photo by writing `null` would silently do
nothing. Writing `""` removes it, and `note`, `name` and `linkedKey` already
read that way.

No download URL is stored. A Firebase download URL is a bearer capability —
anyone holding it reads the object without authentication, bypassing the
Storage rules — and this repository's whole posture is that `/stock` is the
one Worker-readable place where something must not leak. The path keeps every
read behind the rules.

### In Cloud Storage

```
stock-photos/{stockDocId}/{photoId}.jpg
```

- `{stockDocId}` is `Keys.stockDocId(record.key)` — the immutable identity. A
  display rename never moves a photo.
- `{photoId}` is a fresh opaque id per upload, **never** a fixed `photo.jpg`.
  That is what makes replacement non-destructive, makes two simultaneous
  replacements resolvable, and makes the cache key change when the picture
  changes.
- `.jpg` because the pipeline always re-encodes to JPEG, so the extension is
  a fact rather than a guess about the source.

Object metadata set on upload: `contentType: image/jpeg`, plus custom
metadata `key` (the logical stock key) and `byUid`. Metadata is for forensics
and cleanup, never for access control — the rules do not read it.

## The write contract

Three operations, all of them through the existing `StockStore` seam.

**Set or replace**

1. Compress and rotate locally. Nothing has left the device yet.
2. Upload to a **new** `{photoId}`. If this fails, stop: the stock document is
   untouched and the existing photo is exactly where it was.
3. In one transaction: read the stored `q`, `min` and `photoPath`; write the
   stock document with `photoPath` set to the new path, `q` and `min`
   re-asserted from what was read, `lastAction: "photo"`, and the audit
   metadata. Return the **previous** path.
4. Delete the previous object, best effort.

**Remove**

1. In one transaction: read the stored `q`, `min` and `photoPath`; write
   `photoPath: ""` with `q` and `min` re-asserted and `lastAction: "photo"`.
   Return the previous path.
2. Delete that object, best effort.

**Two people replacing at once.** Both upload, so two new objects exist. Both
run the swap. Firestore serialises them: the second transaction reads the
first's path and returns *that* for deletion. One object is referenced, one is
deleted, and neither person's upload was destroyed before it was superseded.

**When cleanup fails.** A failed delete leaves an unreferenced object. It is
not reachable from any stock row and it is not a correctness problem — it is
storage nobody is using. Sweeping it needs either a scheduled Cloud Function
(new infrastructure, new cost) or a manual script. See the open decisions.

**What a photo write must not do:** write a `/stockMoves` document; change `q`
or `min`; change `off`; or touch `pinned`. `StockWriteTest` asserts each of
those.

## Access rules

### Firestore

Two small changes to `firestore/firestore.rules`:

1. Add `'photo'` to the `lastAction` list on `/stock` create and update, so a
   Staff member may make a photo change. The list becomes
   `['in','out','min','add','pin','note','photo']`.
2. Add a guard beside `noPriceData()` and `safeName()`:

```
function safePhotoPath() {
  return request.resource.data.get('photoPath', '') is string
    && (request.resource.data.get('photoPath', '') == ''
        || request.resource.data.photoPath.matches('^stock-photos/[^/]+/[^/]+$'));
}
```

A stock row may only point at a path in the photo tree. `'photo'` is
deliberately **not** added to the `/stockMoves` action list: nothing moved.

### Cloud Storage

A new `firestore/storage.rules`, and a `storage` block in `firebase.json` so
it can be deployed and emulated:

```
match /stock-photos/{stockDoc}/{photo} {
  allow read:   if signedIn() && activeMember();
  allow write:  if signedIn() && stockWriter()
                && request.resource.size < 2 * 1024 * 1024
                && request.resource.contentType == 'image/jpeg';
  allow delete: if signedIn() && stockWriter();
}
```

**One external fact this plan could not verify here.** `activeMember()` and
`stockWriter()` need the caller's role, which lives in `/users/{uid}` in
**Firestore**, not in the auth token. Cloud Storage rules reading Firestore is
a documented cross-service feature, but `firebase.google.com` is blocked by
this environment's egress proxy, so it could not be confirmed against the
official documentation in this session. **Confirming it is the first step of
batch A**, because the fallback is materially worse:

- *If cross-service rules work*, roles come from `/users/{uid}` and Storage
  enforces the same matrix as Firestore.
- *If they do not*, Storage rules can only see `request.auth`. Reads would
  degrade to "any signed-in member" (acceptable — that is already who may read
  `/stock`), but **writes** could not be limited to Owner/Admin/Staff by rules
  alone. Closing that would need custom claims on the auth token, which needs
  the Admin SDK — a Cloud Function and a new moving part. That is a real
  change in scope and cost, and the Owner should decide it rather than
  discover it.

## Android integration

| Piece | Choice | Why |
|---|---|---|
| Camera | `ActivityResultContracts.TakePicture()` into a `FileProvider` URI under `cacheDir/stock-photos/` | No `CAMERA` permission, and the file lands somewhere we already have a provider for |
| Gallery | `ActivityResultContracts.PickVisualMedia()` | The system photo picker; no storage permission at any API level, and it degrades gracefully below Android 13 |
| Manifest | **Unchanged** | No new permission. One line added to `res/xml/file_paths.xml` |
| Orientation | `androidx.exifinterface` | `ImageDecoder` handles EXIF itself but is API 28+; `minSdk` here is 23 |
| Compression | Decode with `inSampleSize`, bound the long edge, re-encode JPEG | Keeps the upload small without a new image library |
| Display | Coil 3, already present, with the storage path as the explicit disk-cache key | Cached photos stay viewable offline, and the key changes when the photo does |
| Upload | `com.google.firebase:firebase-storage` from the existing Firebase BoM | One new dependency, version managed by the BoM already in place |

The decisions inside the pipeline — target long edge, JPEG quality, the
sample size for a given source size, and the rotation implied by each EXIF
orientation value — go in a pure `domain/StockPhoto.kt` so they are unit-tested
without Android. Only the bitmap decode/encode touches the platform. This is
the same split that made the rest of N3 testable.

Per the settled rule, every dialog body is an internal panel the tests drive
directly, and the `AlertDialog` is a wrapper holding no logic. The preview
sheet holds an unconfirmed choice, so it uses the same non-dismissible
properties Add stock uses.

## Firebase Storage: setup, billing and cost

### Verified from official documentation

Cloud Storage for Firebase now requires the pay-as-you-go **Blaze** plan —
including for the *default* bucket. Google's own FAQ for the September 2024
change states that from **30 October 2024** a project must be on Blaze to
provision a new default bucket, and that by **1 October 2025** keeping access
to existing storage resources also requires Blaze; a project left on the
no-cost Spark plan has access to no Cloud Storage bucket at all and its API
calls return **402 or 403**. Both of those dates are in the past. No-cost
usage allowances still exist *within* the Blaze plan.

The default Storage security rules require Firebase Authentication for any
read or write (`allow read, write: if request.auth != null`), so a new bucket
is not open to the world — but it is open to every signed-in account, which is
why the rules above replace it rather than extend it.

### Repository findings, separate from project settings

- The committed **placeholder** `google-services` files name a
  `storage_bucket` of `smartie-quote-desk-staging.firebasestorage.app`. That
  is the default naming convention appearing in a placeholder — it is **not
  evidence that a bucket exists**. The real config arrives from a CI secret
  this session cannot read.
- `firestore/firebase.json` has no `storage` block, so nothing in this
  repository can deploy or emulate storage rules today.
- No Firebase Storage dependency is declared in `app/build.gradle.kts`.

### What cannot be verified without project access

Whether `smartie-quote-desk-staging` is on Spark or Blaze; whether a default
bucket exists; its location; and whether a billing account is attached. None
of that is in the repository, and no session holds a credential. **The Owner
must check the console.**

### Owner setup required

1. Upgrade `smartie-quote-desk-staging` to Blaze and attach a billing account.
2. Provision the default Storage bucket, choosing its location deliberately —
   a bucket's location is permanent, and `asia-south1` (Mumbai) is the obvious
   fit for this business.
3. Set a **budget alert** on the billing account before any of this is used.
4. Later, the same for production at cutover. Production is out of scope here.

### Expected cost

Small, but stated as a shape rather than a number I could not verify. With 403
catalogue products, if half of them ever get a photo at roughly 250 KB each
that is on the order of **50 MB stored** — trivial. Downloads are bounded by
Coil's disk cache: each device fetches a given photo about once. Operations
are a handful per photo change.

I could not read the current no-cost allowance figures: `firebase.google.com`
is blocked by this environment's egress proxy, and search results did not
surface the exact numbers. **The Owner should read the allowance off
`firebase.google.com/pricing` directly** rather than take a figure from here.
The honest summary is that this feature's volume is very small, and that the
Blaze requirement is a *plan* requirement, not a prediction of a bill.

**If the Owner does not want Blaze**, there is a fallback that keeps the
feature but changes its shape — see the open decisions.

## Test plan

**Pure (JVM):** `StockPhotoTest` — the path for a catalogue key and for a
manual key; that a display rename produces the same path; that two uploads
never produce the same object id; the sample size chosen for a range of source
dimensions; the rotation for each EXIF orientation value; that the output is
bounded on its long edge; that a blank path reads as "no photo".

**Write path:** `StockPhotoWriteTest`, against the existing fake store —
a set writes `photoPath`, `lastAction: "photo"` and **no movement**; `q` and
`min` come from the stored values and are unchanged; a remove writes `""`;
the transaction returns the displaced path; a replayed transaction body stays
correct; two sequential swaps leave the second path live and return the first
for deletion; an upload failure leaves the document untouched.

**Rules (emulator):** Staff may write `lastAction: "photo"`; a Worker may not;
a `photoPath` outside the photo tree is refused; a non-string `photoPath` is
refused; `'photo'` is refused on `/stockMoves`; and — in `storage.test.js` —
a Worker may read an object and not write one, a Staff member may write, an
over-size or non-JPEG upload is refused, and a signed-out caller gets nothing.

**Compose (Robolectric):** the source sheet offers exactly two options; the
preview does not upload until confirmed; cancel uploads nothing; a Worker sees
a thumbnail and a larger view but no add, replace or remove; offline every
control is disabled and says so; a row with no photo shows no broken
placeholder; the thumbnail is present when `photoPath` is set.

**Manual, on staging** (adds to the T-S rows; the N3 rows still stand):

## Open decisions

These change behaviour or cost, and are the Owner's.

1. **Blaze on staging — the blocking one.** Cloud Storage cannot be used at
   all without it. If the answer is no, the fallback is a *small* photo stored
   as bytes in Firestore rather than in Storage: it needs no bucket and no
   plan change, but it would have to be a thumbnail of roughly 30–50 KB, it
   inflates the `/stock` document every device downloads on every board read,
   and it puts image bytes in a collection the PWA also reads. It is a real
   option and a worse one; it should be chosen deliberately if at all.
2. **Cross-service Storage rules.** Confirm they can read `/users/{uid}`. If
   not, decide between weaker write rules or custom claims via a Cloud
   Function.
3. **One object or two.** A single full-size object that the card downscales
   locally is the smallest thing that works. A separate ~200px thumbnail
   halves what the board downloads but doubles objects, uploads and deletes.
   Recommendation: one object now, revisit if the board feels slow.
4. **Orphan sweeping.** Accept rare unreferenced objects, or add a scheduled
   Cloud Function to sweep them. Recommendation: accept them now — they are
   invisible and nearly free — and revisit if they accumulate.
5. **Bucket location.** Permanent once chosen. `asia-south1` is the obvious
   fit, but it is the Owner's call.
6. **Maximum upload size.** 2 MB after compression is proposed. It bounds
   cost and is enforced in the Storage rules, so raising it later means a
   rules deploy.

## Out of scope for N3.1

Multiple photos per item, photos on products rather than stock rows, photos in
quotations or the PDF, annotation or cropping, barcode scanning, and any
production deployment. Purchase photo attachments belong with N4 if they are
wanted at all. None of this changes N3's quantity, archive or permission
behaviour, and N3.1 must not be allowed to become the reason N3's outstanding
device checks slip.
