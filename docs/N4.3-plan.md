# N4.3 — Staff owns what it raised; History for everyone

*The plan of record for this batch. Every decision below is the Owner's,
taken after a staging phone pass on the run #106 build, and recorded here
rather than re-derived.*

## Why

The N4.2 phone pass passed T-C1, T-C3, T-C4, T-C15 and the Staff "no History"
part of T-C5, and produced three changes of requirement.

A **Staff** account could raise a requirement and then watch somebody else
record the delivery against it. That is the wrong way round on a shop floor:
the person who noticed the shortage is usually the person standing in front of
the van when it arrives. N4.2 gave them Edit, Urgency and Remove on their own
untouched requirement; this batch gives them **Receive** and **Close with N
received** as well.

Everybody needs **History**, not just the roles that manage. And the Add and
Edit sheets lose the Note field and the buttons behind the keyboard on a real
phone, which no amount of scrolling makes acceptable.

## Receiving does not touch stock

Checked before anything else was planned, because the Owner would have had to
decide whether a Staff account may move stock. It does not arise.

`PurchaseWriteRepository` is built with `FirestorePurchaseStore(firestore)`
alone (`AppContainer.kt`), and that store reads and writes exactly one
collection — `PurchaseStore.PURCHASE = "purchase"`. `PurchaseWrite`,
`PurchaseAccess`, `PurchaseWriteRepository` and `PurchaseViewModel` contain no
executable reference to stock. `stocked` and `stockedQty` are read by
`OperationsReaders` and written nowhere; they are the PWA's. The rules agree
independently: `stockWriter()` is `admin() || staff()`, so a `worker` cannot
write `/stock` or `/stockMoves` whatever the app does.

## The role matrix after this batch

Stored values are unchanged throughout: Owner `owner`, Administrator `admin`,
Manager `staff`, Staff `worker`.

| Action | Owner | Administrator | Manager (`staff`) | Staff (`worker`) |
|---|---|---|---|---|
| Read, Create | ✅ | ✅ | ✅ | ✅ |
| Edit / urgency — **untouched** | ✅ | ✅ | ✅ any row | ✅ **own row only** |
| Edit / urgency — **any receipt** | ✅ | ✅ | ❌ | ❌ |
| **Receive** (partial and full) | ✅ | ✅ | ✅ any row | ✅ **own row only** |
| **Close with N received** | ✅ | ✅ | ✅ any row | ✅ **own row only** |
| Reopen | ✅ | ✅ | ❌ | ❌ |
| Soft-remove — untouched | ✅ | ✅ | ✅ own row only | ✅ own row only |
| Soft-remove — any receipt | ✅ | ✅ | ❌ | ❌ |
| Hard delete | ❌ | ❌ | ❌ | ❌ |
| Purchase History — received rows | everyone's | everyone's | everyone's | **own only** |
| Purchase History — removed rows | everyone's | everyone's | everyone's | **own only** |

"Own" always means **`byUid` is non-blank and equals the viewer's uid**. Never
a display name, never an email, and never a row whose author cannot be proved.

## The post-receipt lock stays

Once a delivery is recorded, the creator keeps Receive and Close-with and
loses Edit, Urgency and Remove. The Owner asked whether to keep that; it
stays, and the reason is worth writing down. A row with a receipt is a record
of what arrived. The person who raised it should be able to finish it — record
the rest, or write off what is not coming — and should not be able to rename
it or take it off the list behind the receipt. Gaining the delivery controls
does not weaken the lock; it removes the reason somebody would resent it.

A reopen still clears the receipt, so the row becomes untouched again and the
creator regains all five controls. That is unchanged from N4.2.

## History is filtered in the app, not in the rules

**Deliberately, and this must not be re-proposed without the condition below
being met.**

Firestore evaluates a list query against its *constraints*, not document by
document. The moment a read rule mentions `resource.data`, an unconstrained
listener is refused — and the app would have to query `where('del','==',false)`
for the open list. Legacy rows carry `del: 1` as a number, or no `del` field at
all; the in-repo fixtures show both. That query would silently drop every one
of them, which `docs/N4-plan.md` calls worse than the read cost. It would also
refuse the PWA's own listener in the same project.

So the read rule stays `allow read: if member()`, the listener stays
unconstrained, and History filters in `domain/PurchaseHistory.kt`.

**Deferred, recorded in `docs/PROJECT-STATUS.md`:** *rules-level restriction on
reading other people's Purchase history — only after the PWA is retired,
together with a one-time `del` normalisation.*

### What counts as removed

The reader already coerces, and this batch adds no second coercion:

| Stored `del` | Reads as |
|---|---|
| absent, `false`, `0`, `"0"` | **active** |
| `true`, `1`, `"1"`, `"yes"` | **removed** |

`bool("del","deleted")` → `asBoolOrNull`, where `is Number -> toDouble() != 0.0`
and the string forms are handled. The Kotlin tests pin each value for each
role rather than re-implementing it.

## Removed by, and when

The soft delete records `del: true` and `deletedBy` (a uid), plus `updated`,
`upBy`, `upUid` and `serverAt` from the shared update base. There is no
dedicated name or time, and `upBy`/`updated` are overwritten by any later
Administrator edit — right for almost every row, and silently wrong for the
ones that matter.

So the soft delete gains **`delBy`** (display name) and **`delAt`** (epoch
millis), mirroring the existing `rcvBy`/`rcvAt` pair.

In the rules they are constrained rather than merely permitted, and
`deletedBy` — which was permitted without any constraint on its value — is
pinned to the caller:

- `delBy` is a string of at most 80 characters;
- `delAt` is a number;
- `deletedBy`, when written, equals `request.auth.uid`.

**No comparison against `request.time`.** A removal made offline carries the
device's clock and syncs later; a server-time bound would refuse it.

A legacy removed row carrying neither field still renders: the name is
resolved from `deletedBy` through the team members the shell already holds,
and with nothing resolvable the row reads simply **"Removed"**.

## Order of the open list

The viewer's own requirements first, then everyone else's, urgency order
inside both groups:

```
compareBy<PurchaseRecord> { if (isMine(it)) 0 else 1 }
  .thenBy { it.urgency.rank }
  .thenByDescending { addedAt(it) }
  .thenByDescending { it.id }
```

`isMine` is `viewerUid.isNotBlank() && record.byUid == viewerUid`, so a blank
`byUid` always sorts as somebody else's.

**The tie-break inside a colour is unchanged: newest first by `addedAt`** —
the reader's `t` → `createdAt` → `updated` fallback — **then by document id,
descending.** The id tie-break exists because a PWA import writes many rows
carrying one timestamp, and a comparator that called them equal would let a
`LazyColumn` keyed by id reorder itself between recompositions under the thumb.

`viewerUid` defaults to empty, which means "nobody's rows come first" and
leaves every existing call site and test describing what it meant.

## The sheets

The Note field must be visible without scrolling, and with the keyboard up the
focused field and the Cancel / Add buttons must stay visible.

- `SmartieField` gains two defaulted parameters: `keyboardActions`, and a
  `fieldModifier` applied to the `OutlinedTextField` itself — its existing
  `modifier` goes on the outer `Column`, so focus and bring-into-view had
  nowhere to attach.
- `PurchaseFormPanel` becomes a weighted scrolling area with the actions
  pinned beneath it and `imePadding()` on the whole panel.
- `PURCHASE_FORM_PROPERTIES` gains `decorFitsSystemWindows = false`. Without
  it a dialog's own window never sees the IME and `imePadding()` is a no-op —
  this is the line that actually makes the keyboard behave.
- Keyboard actions run Next → Next → Done.

### The urgency picker

`docs/N4-plan.md` rejected a segmented control because "Needed, but not now"
and "Can wait 1-2 days" clip at 360dp with `maxLines = 1`. Three full-width
48dp rows are exactly what pushes Note off the sheet.

So: **three compact coloured chips on one row**, faces **Urgent** /
**1-2 days** / **Not now**, with the selected option's **full Owner wording
shown beneath the row** and set as each chip's `contentDescription`. The
wording stays on screen and stays unchanged; only the chip face is short.
`UrgencyV2.wireValue` and `UrgencyV2.label` are untouched, so nothing on the
wire and nothing on a card moves. The default urgency is unchanged.

## The PWA

**The rules change does not break it.** It only widens who may write — one new
alternative inside the existing creator branch, two field names added to the
remove list, and three value constraints. No read rule changes, no query
changes, nothing becomes newly required, and nothing the PWA writes today
stops being accepted. A receipt a Staff account records is an ordinary
receipt.

The standing cutover restriction is unchanged: the PWA overwrites `rcvQty` and
carries no `rev`, so the two apps must still never both write Purchase
requirements in one project.

## Deployment

**Both halves, one sitting.** A staging rules deploy and one new APK, built at
the end of the batch. On the old rules a Staff account would see Receive and
be refused by the server; on the old APK the widened rules go unused.

`firestore/firestore.indexes.json` is **unchanged** — no new query — so no
index deploy is needed.
