# N4.2 — Creator self-service on Purchase requirements

*The plan of record for this batch. Audited read-only before a line was
changed; every decision below is the Owner's, recorded here rather than
re-derived.*

## Why

A requirement is usually raised by the person who noticed the shortage, and
they are the person most likely to notice a typo in it a minute later. Until
now a **Staff** account (stored `worker`) could add a requirement and then do
nothing at all to it — not even correct the quantity they had just mistyped —
while a **Manager** could edit anybody's requirement for ever, including one
that had already been half delivered.

Both ends of that were wrong. This batch gives the creator a short window to
correct their own work, and closes the record the moment a delivery touches
it.

## Titles are not identities — the mapping this batch does not change

| Shown to a person | Kotlin `Role` | Firestore `users/{uid}.role` | Rules predicate |
|---|---|---|---|
| Owner | `Role.OWNER` | `owner` | `owner()` |
| Administrator | `Role.ADMIN` | `admin` | `admin()` |
| **Manager** | `Role.STAFF` | `staff` | `staff()` |
| **Staff** | `Role.WORKER` | `worker` | `worker()` |

**No role value is renamed and no account is migrated.** The stored
vocabulary is the PWA's and stays exactly as it is; `RoleTitles` is the only
place it becomes words. The one correction this batch makes is to two
**emulator display names** — the `staff` test account was called "Staff" and
the `worker` one "Worker", which is precisely the confusion this table exists
to prevent. The uid keys and the stored `role` values are untouched.

## What "untouched" means

A requirement is **untouched**, and therefore still its creator's to correct,
when *all* of these hold of the **stored** document:

- it is Open — `status == 'Needed'`
- it is not soft-removed — `del != true`
- it is not received — `received != true`
- it carries **none** of `rcvQty`, `rcvBy`, `rcvUid`, `rcvAt`
- consequently `receivedTotal == 0`

Decided against `resource.data` in the rules and against the document read
**inside the transaction** in the app — never against the copy the screen was
holding, which may be two deliveries old.

## Ownership

`member.uid == record.byUid`, and nothing else. Never a display name, never an
email: two people called Ravi must not inherit each other's permissions.

`byUid` is written once, by `PurchaseWrite.create`, and the create rule
refuses the document unless `request.resource.data.byUid == request.auth.uid`.
No update payload has ever contained it, and after this batch the rules pin it
on **every** branch, the Administrator's included.

**A legacy or PWA row with no `byUid` fails closed.** `resource.data.get('byUid', '')`
is `''`, which never equals a signed-in uid, so nobody gets creator rights over
a row whose author cannot be proved. Three of the four in-repo fixtures are
exactly that shape.

## The role matrix after this batch

| Action | Owner | Administrator | Manager (`staff`) | Staff (`worker`) |
|---|---|---|---|---|
| Read | ✅ | ✅ | ✅ | ✅ |
| Create | ✅ | ✅ | ✅ | ✅ |
| Edit name/note/quantity — **untouched** row | ✅ | ✅ | ✅ any row | ✅ **own row only** |
| Edit — **row with any receipt** | ✅ | ✅ | ❌ | ❌ |
| Change urgency — untouched | ✅ | ✅ | ✅ any row | ✅ **own row only** |
| Change urgency — any receipt | ✅ | ✅ | ❌ | ❌ |
| Mark received | ✅ | ✅ | ✅ | ❌ |
| **Close a shortfall** | ✅ | ✅ | ✅ | ❌ |
| Reopen | ✅ | ✅ | ❌ **now refused by the rules** | ❌ |
| Soft-remove — untouched | ✅ | ✅ | ✅ **own row only** | ✅ **own row only** |
| Soft-remove — any receipt | ✅ | ✅ | ❌ | ❌ |
| Hard delete | ❌ | ❌ | ❌ | ❌ |

**The Manager-reopen gap closes.** `docs/N4-plan.md` has recorded reopen as
"the one purchase restriction the rules cannot express" since Batch 2. It is
expressible now, and not by a special case: a reopen removes `rcvQty`, and the
Manager branch refuses any write that reduces the received total.

## Reopen restores creator access — the Owner's decision

When an Owner or Administrator reopens a requirement, the four `rcv*` fields
are **removed**, which is what returns the cumulative total to zero. The row is
then untouched by the definition above, and its creator may correct it again
until another delivery arrives.

**No `everReceived` marker is added.** It was considered and rejected: the
rules can only see the stored document, so "was ever received" would need a new
persisted field and a schema change, and reopen is an Owner/Administrator
action that deliberately erases the receipt. A row that has been reopened is
meant to be as good as new.

## The seventh operation — closing a shortfall

Ten were wanted, seven came, and the last three are not coming. Until now the
only way to record that was to edit the required total down to seven, which
this batch makes Owner/Administrator-only on a row with a receipt — so a
Manager would have been left unable to clear a requirement they could see was
finished.

`PurchaseWrite.closeShortfall` is therefore an **explicit, named seventh
operation**, and deliberately not a generic `setStatus` and not a Cancel. It
takes no quantity from the caller at all:

- available to **Owner, Administrator and Manager**, never to Staff;
- only while the stored row is Open, not removed, and **partly** received —
  `0 < receivedTotal < qty`, with `rcvQty` stored as a **number**;
- inside one transaction it re-reads the document, confirms it is still partly
  received, and sets `qty` **exactly equal to the stored `rcvQty`**;
- sets `received: true` and `status: 'Received'`;
- **preserves** `rcvQty`, `rcvBy`, `rcvUid` and `rcvAt` — the receipt is a
  record of a delivery and is not rewritten by the person writing off the rest;
- advances `rev` and writes the ordinary `upBy` / `upUid` / `updated` /
  `serverAt` audit fields;
- an `ABORTED` conflict is **never** retried automatically.

The confirmation says what will happen in full, because it changes a stored
quantity:

> **Close with 7 received**
> Required quantity will change from 10 to 7 and the requirement will be
> closed. The remaining 3 will be written off.

## A stored `rcvQty` must be a number

For a Manager, both the receipt branch and the shortfall branch require the
stored `rcvQty`, where it exists, to be **numeric**. A legacy row holding
`"4"` fails closed for a Manager rather than being compared or coerced inside
the rules, where a mixed-type comparison raises an error and the failure mode
is not worth relying on. An Owner or Administrator rescues such a row through
the privileged edit path — the same shape as the existing legacy-`qty` rescue.

## The Firestore rules

Inside `match /purchase/{id}` only. `allow read`, `allow create` and
`allow delete: if false` are unchanged; `worker()`, `staff()`, `admin()`,
`touched()` and `revOk()` are unchanged.

```
allow update: if member()
              && request.resource.data.id == id
              && request.resource.data.qty is number && request.resource.data.qty > 0
              && request.resource.data.updated is number
              && revOk()
              && prIdentityPinned()
              && (
                   admin()
                   || (staff() && (
                        (prUntouched() && prEditKeys())
                        || (prReceiptKeys() && prRcvNumeric() && prRcvNotReduced())
                        || (prShortfall() && prShortfallKeys())
                      ))
                   || (prCreator() && prUntouched()
                       && (prEditKeys() || prRemoveKeys()))
                 );
```

`!worker()` is gone from the front of the rule and replaced by branch
structure. That is the whole of the change in shape.

`prIdentityPinned()` holds `id`, `by`, `byUid` and `t` equal before and after
on **every** branch. An immutable field should not depend on which branch
happened to match, and a legacy row carrying none of them still passes, because
`'' == ''`.

A creator who is also a Manager needs no fourth branch: the third grants them
soft-removal of their own untouched row, which the Manager branch alone does
not.

### The allowed-field lists

`touched().hasOnly(...)`, derived from what the app actually writes.
`PurchaseWrite.base()` is `{id, qty, updated, rev, upBy, upUid, serverAt}`, and
`serverAt` changes on every write so it is always present.

| Branch | Keys |
|---|---|
| Creator / Manager **edit** | `name`, `note`, `qty`, `urgency`, `updated`, `rev`, `upBy`, `upUid`, `serverAt` |
| Creator **soft-remove** | `del`, `deletedBy`, `updated`, `rev`, `upBy`, `upUid`, `serverAt` — **`qty` excluded**, so a removal cannot smuggle a quantity change |
| Manager **receipt** | `status`, `received`, `rcvQty`, `rcvBy`, `rcvUid`, `rcvAt`, `qty`, `updated`, `rev`, `upBy`, `upUid`, `serverAt` |
| Manager **shortfall** | `status`, `received`, `qty`, `updated`, `rev`, `upBy`, `upUid`, `serverAt` — **no `rcv*` key at all**, so the receipt cannot be rewritten while writing off the rest |

Everything else is refused by `hasOnly` rather than by a list of prohibitions:
`id`, `by`, `byUid`, `t`, `key`, `stocked`, `stockedQty`, `cancelledBy`,
`cancelledUid`, `cancelledAt`, and `status` / `received` / `rcv*` outside the
branches that own them.

**Deleting a key counts as touching it**, which is what stops a malicious
client clearing `rcvQty` and then editing: the removal puts `rcvQty` in
`touched()`, and `hasOnly` rejects it. `prUntouched()` reads the stored
pre-state, so the attempt fails there first as well. Two independent guards.

## Purchase History — binding requirement for Batch 5

**Staff will see their own history only.** When the read-only Purchase History
screen is built:

- a Staff account sees exactly the rows where `record.byUid == member.uid`;
- **legacy rows with no `byUid` are not in a Staff account's own history**, for
  the same reason they grant no creator rights: the author cannot be proved;
- Manager, Administrator and Owner keep the full team history the N4 plan
  already describes;
- **until that filtering exists, the Purchase History entry stays hidden from
  Staff**, which is what `MoreDestinations` does today.

Nothing in this batch implements any of it.

## Rollout

The rules get **stricter** for a Manager as well as looser for Staff, so a
Manager still running the Batch C build would be offered Edit on a received row
and be refused by the server. The order is therefore:

1. this branch lands and CI is green;
2. the **Owner** deploys the rules to **staging only**;
3. the new APK goes on **every** phone in the same sitting.

Staff's new abilities are the safe direction — an old build simply does not
offer them. The Manager restriction is the one that must not run ahead of the
APK.
