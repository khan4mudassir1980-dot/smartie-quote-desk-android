# N3.1 Stock Photo — plan (Spark revision 2)

One optional photo per stock item, stored in Firestore, on the **Spark** plan.
Proposed, not built: nothing here is implemented, no dependency has been
added, and no Firebase project has been touched.

**The decision that shapes this document:** SMARTIE stays on Firebase Spark.
No billing account, no Blaze upgrade, no Cloud Storage, no Cloud Functions, no
paid service. Cloud Storage requires Blaze even for a default bucket, so it is
not an option to hold in reserve.

N3.1 sits on top of N3, which is **open** — single-device staging
verification passed, physical two-device concurrency verification pending
(`docs/N3-verification.md`). N3.1 changes no settled N3 behaviour.

## Units used throughout

`KiB` = 1,024 bytes, `MiB` = 1,024 KiB, `GiB` = 1,024 MiB. The photo ceiling
is **80 KiB = 81,920 bytes**, which is the figure the security rule enforces.
Google's quota figures are quoted in the units the source uses. No figure in
this document mixes decimal KB with binary KiB.

## Verdict

**The design is suitable and is the right shape for Spark.** One of its
choices is forced rather than merely tidy, and the rest are sound. It needs
the refinements below, and it carries limitations that must be accepted with
open eyes.

I am **not** recommending that photos be postponed. The conditions under which
I would are at the end.

### The facts this design lives with

| Fact | Source | Consequence |
|---|---|---|
| Maximum document size **1 MiB** | [Usage and limits](https://firebase.google.com/docs/firestore/quotas) | An 80 KiB photo uses about 8% of one document. Comfortable |
| **The mobile SDKs have no `select()` projection** — server SDKs only | [Client libraries](https://firebase.google.com/docs/firestore/client/libraries) | Android cannot fetch a document without one of its fields. A photo on `/stock` would be downloaded by every device on every board read with no way to opt out. **The separate photo document is mandatory** |
| Indexed field values are **truncated after 1,500 bytes**; the index-entry ceiling is **7.5 KiB** | [Index types](https://firebase.google.com/docs/firestore/query-data/index-overview) | A large `bytes` field is truncated in its index entry, **not rejected**. Writes succeed without an exemption. The exemption is still worth having — see below — but nothing breaks without it |

### Why the index exemption stays

Not because writes fail. Because:

- **Index storage is charged against the 1 GiB stored allowance.** An
  automatically indexed field costs two index entries per document, ascending
  and descending, each up to the 1,500-byte truncation. For 403 photo
  documents that is roughly `403 × 2 × 1.5 KiB ≈ 1.2 MiB` of index holding
  truncated fragments of JPEG-ish bytes.
- **The index is useless.** Nobody will ever order or filter by the first
  1,500 bytes of an image.
- **Write latency and cost.** Every write maintains those entries for nothing.

So the `fieldOverrides` entry ships in batch A as good practice, and **its
absence is no longer a release blocker**. That removes the ordering constraint
the previous revision imposed on the batches.

### Refinements

1. **`hasPhoto` and `photoRev` on the stock row.** Without them the app cannot
   tell which rows have photos without reading every photo document. The board
   already downloads every `/stock` document, so both fields are free.
2. **`photoRev` is the cache key and the concurrency guard**, and it is
   monotonic — see the caching and conflict sections.
3. **Fetch photo bytes lazily, cache-first, per row scrolled into view** —
   never a bulk prefetch.

### Limitations

1. **Photos share every quota with the rest of the app.** There is no separate
   photo budget.
2. **Dimensions are not enforceable by rules.** Rules can check
   `bytes.size()`; they cannot decode an image. 800×800 is a client-side
   promise. The byte ceiling is the enforceable half.
3. **Image quality at this budget is unproven** and is settled by a manual
   acceptance check on real stock items, not by arithmetic here. See
   "Image quality".
4. **Photo bytes compete for the on-device Firestore cache**, which evicts
   least-recently-used data; evicted data costs reads to fetch again.

## The user flow

A stock card with no photo shows a small camera affordance to anyone who may
manage photos. Tapping it offers exactly two options — **Take a photo** and
**Choose from gallery** — the same two-mode shape Add stock uses. Either route
lands on a **preview** with **Add photo** and **Cancel**. Nothing is written
until Add photo is pressed.

A card with a photo shows a thumbnail; tapping it opens a larger view. A
Worker gets the thumbnail and the larger view and nothing else. The larger
view carries **Replace** and **Remove** for anyone who may manage photos.

Offline, every photo control is disabled with the wording the stock controls
already use, and a photo already cached on the device stays viewable.

## Data model

### On `/stock` — two small fields

| Field | Type | Meaning |
|---|---|---|
| `hasPhoto` | boolean | Whether a photo document exists. Absent means false |
| `photoRev` | number | Monotonic. Increments on every set, replace and remove |

No image bytes ever touch `/stock` — the collection a Worker reads, and the
one the PWA also reads.

### `/stockPhotos/{stockDocId}` — the bytes

| Field | Type | Meaning |
|---|---|---|
| `key` | string | The logical stock key, for forensics and a later migration |
| `bytes` | bytes | The WebP image, ≤ 81,920 bytes. Exempt from indexing |
| `w`, `h` | number | Pixel dimensions, so the card can lay out before decoding |
| `rev` | number | Must equal `/stock.photoRev` after the commit |
| `by`, `byUid` | string | Who last set it |
| `at`, `serverAt` | number, timestamp | The repository's existing audit pair |

The document id is `Keys.stockDocId(record.key)` — the immutable identity, so
a display rename cannot move or orphan a photo. Firestore's native `bytes`
type is used, not base64, which would inflate the payload by about a third.

### The index exemption

`firestore/firestore.indexes.json` gains one `fieldOverrides` entry:

```json
{
  "collectionGroup": "stockPhotos",
  "fieldPath": "bytes",
  "indexes": []
}
```

## Image quality — decided by manual acceptance, not by arithmetic

800×800 at 80 KiB is about 1.0 bit per pixel, which for WebP lossy is in the
region of a JPEG at quality 75–80. Whether that is **good enough for SMARTIE's
actual stock** is not something this document can settle, and it should not
pretend to.

**T-P4 is the acceptance check**: photograph real items off the real shelves —
a gate motor, a boom barrier, a boxed accessory, and one item whose
distinguishing feature is printed text — and judge the results. It passes if
the photos do the job they are for. If printed text turns out to be the point
and 80 KiB cannot deliver it, that is a finding that sends the ceiling or the
whole feature back for review, not something to quietly retune.

**Encoding:** long edge scaled to at most 800 px, then WebP lossy with quality
searched downwards until the result is ≤ 81,920 bytes. Quality floats; the
ceiling does not. If the floor is reached without fitting, the save is refused
with an explanation rather than storing something worse.

## Caching: revision-matched, or not used at all

The cache holds `stockDocId → (rev, bytes)`. The stock listener already
delivers `hasPhoto` and `photoRev` on every board update, so the check costs
nothing.

| Stock row says | Cache holds | Action | Reads spent |
|---|---|---|---|
| `hasPhoto: true`, `photoRev: n` | `rev == n` | **Use the cached bytes** | 0 |
| `hasPhoto: true`, `photoRev: n` | `rev < n` | Discard, fetch, store at `n` | 1 + rule read |
| `hasPhoto: true`, `photoRev: n` | nothing | Fetch, store at `n` | 1 + rule read |
| `hasPhoto: false` | anything | **Discard; show no photo** | 0 |

Two rules follow, and both matter:

- **Never serve bytes whose `rev` does not match the row.** A replaced photo
  is stale the moment the row updates, and a stale image on a shelf is worse
  than none.
- **Never re-fetch on a match.** This is what stops unchanged photos being
  downloaded repeatedly, and it is the assumption the whole usage calculation
  rests on. It is checked by hand in T-P14.

A removal invalidates by the same mechanism: `hasPhoto: false` discards the
cached bytes without a read, and `photoRev` still advances so that a device
which never saw the removal cannot later mistake an old cached copy for
current.

Because `photoRev` is monotonic, a device that has been offline and comes back
to a *lower* or equal rev than it holds knows its copy is current; it never
has to guess from timestamps.

## The write contract

All three operations write **both** documents in **one Firestore
transaction**, through the existing `StockStore` seam extended with photo
reads and writes.

**Set or replace.** One transaction: read `/stock` for the stored `q`, `min`
and `photoRev`; write `/stockPhotos/{id}` with the new bytes and
`rev = photoRev + 1`; write `/stock` with `hasPhoto: true`, `photoRev = rev`,
`q` and `min` re-asserted from what was read, `lastAction: "photo"`, and the
audit metadata. Nothing is written before the transaction, so nothing can be
left behind by a failure.

**Remove.** One transaction: delete `/stockPhotos/{id}`; write `/stock` with
`hasPhoto: false`, `photoRev` incremented, `q` and `min` re-asserted and
`lastAction: "photo"`.

**What a photo write must never do:** write a `/stockMoves` document; change
`q`, `min` or `off`; or touch `pinned`.

### Conflict behaviour, defined

Firestore serialises the transactions and re-runs the loser's body against the
winner's committed data. That gives one outcome per case, and each is asserted
by a test:

| Case | Outcome |
|---|---|
| Replace vs replace | Both read `photoRev: n`. One commits `n+1`; the other re-runs, reads `n+1`, commits `n+2`. **The later commit's image survives**, both documents agree, and the superseded bytes are overwritten in place — not left somewhere |
| Replace vs remove, remove commits first | The replace re-runs, sees `hasPhoto: false` at `n+1`, and writes a new photo document at `n+2`. **Net effect: the photo exists.** The later action wins |
| Remove vs replace, replace commits first | The remove re-runs, sees `n+1`, deletes and writes `hasPhoto: false` at `n+2`. **Net effect: no photo** |
| Either racing a quantity change | Independent fields; the photo transaction re-asserts `q` and `min` from what it read inside the transaction, so a concurrent quantity change is either seen or re-run against |

"The later action wins" is deliberate and worth stating out loud: there is no
merge for a photograph, and a rule that surprised people would be worse than
one that is simply last-writer-wins on a monotonic counter.

### Archive behaviour, defined

Archiving is `off: true` on `/stock`; the stock document is not deleted.

- The photo document is **kept**, `hasPhoto` and `photoRev` unchanged.
- The row is hidden from the board, so the photo is not fetched or displayed.
- Un-archiving restores the row with its photo intact.
- The bytes continue to occupy stored capacity — about 60 KiB per archived
  photographed row. At the volumes in the usage section this is not material,
  but it is not free either.

Keeping the photo is consistent with the rest of N3: archiving hides a row,
it does not destroy its history.

### Orphans, qualified

The previous revision said "no orphans possible". That was too strong. What
actually holds:

**Prevented, by the transaction and by rules that refuse an inconsistent
commit:** a photo document without its stock metadata; stock metadata claiming
a photo that does not exist; a `rev` mismatch between the two; and — because
the `/stock` delete rule requires the photo document to be gone after the same
commit — a stock document deleted out from under its photo.

**Not prevented:** writes made through the **Firebase console**, which
bypasses security rules entirely. An Owner editing a document by hand can
create an inconsistency that no rule can stop. The consistency check in the
manual pass is what would find it.

So: **no orphans are reachable through the app**, and console edits are the
documented exception rather than an oversight.

## Access rules

### `/stockPhotos`

```
match /stockPhotos/{stockDoc} {
  function stockPath() {
    return /databases/$(database)/documents/stock/$(stockDoc);
  }
  function stockAfter() { return getAfter(stockPath()).data; }

  allow read: if member();

  allow create, update: if stockWriter()
                && request.resource.data.bytes is bytes
                && request.resource.data.bytes.size() <= 81920
                && request.resource.data.key is string
                && request.resource.data.rev is number
                && request.resource.data.byUid == mine()
                && noPriceData()
                // The stock row must agree, in the same commit.
                && stockAfter().hasPhoto == true
                && stockAfter().photoRev == request.resource.data.rev;

  allow delete: if stockWriter()
                && (!existsAfter(stockPath()) || stockAfter().hasPhoto == false);
}
```

### `/stock`, additionally

```
function photoMetaOk() {
  let after = request.resource.data;
  let photo = /databases/$(database)/documents/stockPhotos/$(key);
  return after.get('hasPhoto', false) == false
    ? !existsAfter(photo)
    : (existsAfter(photo) && getAfter(photo).data.rev == after.photoRev);
}

function photoRevMonotonic() {
  let before = resource == null ? 0 : resource.data.get('photoRev', 0);
  return request.resource.data.get('photoRev', 0) >= before;
}
```

`photoMetaOk()` and `photoRevMonotonic()` join the `/stock` create and update
conditions, and `'photo'` joins the `lastAction` list —
`['in','out','min','add','pin','note','photo']`. `'photo'` is deliberately
**not** added to the `/stockMoves` action list: nothing moved.

The `/stock` delete rule gains `&& !existsAfter(photo)`, so an Administrator
deleting a stock row must delete its photo in the same commit.

**Two corrections this section carries from batch A, where the rules were
actually written** (`69d0fce`; the repository is the authority, this text
follows it):

1. The `/stockPhotos` delete rule reads
   `!existsAfter(stockPath()) || stockAfter().hasPhoto == false`, not
   `stockAfter().hasPhoto == false` alone. The original cannot be evaluated
   when the stock row is deleted in the same commit, which would have made the
   cascade delete above — T-P15 — impossible. Both commit orders are tested.
2. The no-price guard is the existing `noPriceData()` helper rather than an
   inline `hasAny([...])`, so `/stockPhotos` holds exactly the line `/stock`
   already holds and the two cannot drift apart.

**These guards cost reads.** Each `getAfter()` and `existsAfter()` is a
document access billed as a read, and they are counted in the usage formulas
below rather than ignored.

## Spark quotas: three different kinds of limit

They are not interchangeable, and the previous revision blurred them.

| Kind | Limit | Resets |
|---|---|---|
| **Daily operation quotas** | 50,000 document reads/day · 20,000 document writes/day · **20,000 document deletes/day** | Daily, around midnight Pacific |
| **Monthly outbound data transfer** | **10 GiB/month** | Monthly |
| **Stored-data capacity** | **1 GiB** | **Never — it is a ceiling, not a rate** |

Figures per [Usage and limits](https://firebase.google.com/docs/firestore/quotas).
This environment's egress proxy blocks `firebase.google.com`, so these were
supplied from that page rather than read here; they should be re-checked
against the live page before approval, because quotas change.

**What exhaustion actually means, per kind:**

- **A daily operation quota** stops reads or writes until the next daily
  reset. Around midnight Pacific is the middle of the Indian working day, so
  the outage does not simply "clear overnight" — but *when* it clears depends
  on when it was hit, and nothing here should promise a time of day.
- **Monthly transfer** exhaustion lasts until the month turns. There is no
  same-day recovery at all.
- **Stored capacity** does not recover by waiting. It is freed only by
  deleting data. A database at 1 GiB stays there until something is removed.

On Spark there is no billing account, so exhaustion **fails requests; it never
charges and never auto-upgrades**. Failures are **app-wide, not photo-only**:
stock, products and quotations stop too.

The app must degrade honestly: a photo that cannot be fetched shows a
placeholder, never an endless spinner; a refused write reports the refusal and
leaves the existing photo alone; and the existing error mapping gains a
resource-exhausted case so the message names the real cause.

## Usage: formulas, then numbers

### Parameters

| Symbol | Meaning | Average case | Maximum case |
|---|---|---|---|
| `R` | stock rows total | 403 | 403 |
| `P` | rows carrying a photo | 200 | 403 |
| `S` | bytes per photo | 60 KiB | 80 KiB (the ceiling) |
| `V` | photo-doc overhead (fields, name, audit) | 0.3 KiB | 0.3 KiB |
| `T` | stock-doc size | 0.5 KiB | 0.5 KiB |
| `D` | active devices | 8 | 8 |
| `L` | cold starts per device per day | 2 | 2 |
| `C` | photo changes per day | 10 | 10 |
| `W` | other stock writes per day | 30 | 30 |
| `G` | rule reads per guarded operation (`profile()` + `getAfter`/`existsAfter`) | 2 | 2 |
| `X` | transaction retry allowance | 10% | 10% |

### Stored data

```
stored = P × (S + V) + R × T
```

- Average: `200 × 60.3 KiB + 403 × 0.5 KiB ≈ 11.78 MiB + 0.20 MiB ≈ 11.97 MiB`
- Maximum: `403 × 80.3 KiB + 403 × 0.5 KiB ≈ 31.60 MiB + 0.20 MiB ≈ 31.80 MiB`

Against **1 GiB (1,024 MiB)**: **1.2%** average, **3.1%** maximum. Without the
index exemption, add roughly `P × 2 × 1.5 KiB` ≈ 0.6–1.2 MiB of useless index.

### One-off cost, first run per device

```
initial_reads   = P × (1 + G)          per device
initial_transfer = P × S               per device
```

- Average: `200 × 3 = 600` reads and `200 × 60 KiB ≈ 11.7 MiB` per device;
  across 8 devices, **4,800 reads and 93.8 MiB**.
- Maximum: `403 × 3 = 1,209` reads and `403 × 80 KiB ≈ 31.5 MiB` per device;
  across 8 devices, **9,672 reads and 252 MiB**.

The one-off read cost lands inside a single day's 50,000 only if devices are
not all filled at once. **Stagger the rollout** — or accept that the day every
device first opens a photographed board spends about 10–19% of that day's
reads on it.

### Daily reads

```
reads/day = D × L × R                     (a) stock listener cold starts
          + D × (W + C)                   (b) listener deltas
          + D × C × (1 + G)               (c) photo re-fetches after a change
          + C × 2 × G                     (d) rule reads on the two written docs
          + X × (b + c + d)               (e) retries
```

Average case:

| Term | Calculation | Reads |
|---|---|---|
| (a) listener cold starts | `8 × 2 × 403` | 6,448 |
| (b) listener deltas | `8 × (30 + 10)` | 320 |
| (c) photo re-fetches | `8 × 10 × 3` | 240 |
| (d) rule reads on writes | `10 × 2 × 2` | 40 |
| (e) retries at 10% | `0.1 × 600` | 60 |
| **Total** | | **7,108** |

That is **14.2% of 50,000**. Of it, photos account for `(c) + (d) + their
share of (e) ≈ 308 reads, or 0.6% of the daily allowance`. **Term (a)
dominates, and it exists with or without photos** — it is the board's own
listener behaviour, and it is the first thing to look at if reads ever become
a problem.

Maximum case differs only in (c), where every change is to a larger file but
the read count is identical. The read budget is insensitive to photo size; the
transfer budget is not.

### Monthly outbound transfer

```
transfer/month = D × [ P × S            (first fill, once)
                     + C × 30 × S       (changed photos re-fetched)
                     + L × 30 × R × T ] (stock listener traffic)
```

- Average: `8 × [11.72 + 17.58 + 11.81] MiB = 8 × 41.11 MiB ≈ 328.9 MiB` →
  **3.2% of 10 GiB**
- Maximum: `8 × [31.48 + 23.44 + 11.81] MiB = 8 × 66.73 MiB ≈ 534 MiB` →
  **5.2% of 10 GiB**

**The pathological case**, stated because it is the one that bites: if the
on-device cache is cleared daily — reinstalls, "clear data", or eviction under
memory pressure — the first-fill term recurs every day:

```
transfer/month(no cache) = D × P × S × 30
```

- Average: `8 × 200 × 60 KiB × 30 ≈ 2.75 GiB` → **27% of 10 GiB**
- Maximum: `8 × 403 × 80 KiB × 30 ≈ 7.38 GiB` → **74% of 10 GiB**

### Daily writes and deletes

```
writes/day  = C × 2 + W        deletes/day = removals
```

Average: `10 × 2 + 30 = 50` writes — **0.25% of 20,000**. Deletes are
removals only, realistically under 10 a day — well under **20,000**.

### Headroom

Photos should stay inside a stated share, so there is room for N4–N8:

| Budget | Photo share | Leaves for the rest of the app |
|---|---|---|
| Daily reads | ≤ 5% (2,500) | ≥ 95%, against the 14.2% the board already uses |
| Monthly transfer | ≤ 10% (1 GiB) | ≥ 90% |
| Stored data | ≤ 10% (102 MiB) | ≥ 90%, which the maximum case (31.8 MiB) sits well inside |

**Trigger:** if the console's usage tab shows photos above those shares, move
to the icon-on-card variant in open decision 1 before adding anything else.

## Migrating to Cloud Storage later

If SMARTIE ever moves to Blaze, the exit stays cheap: the pointer is already
indirect (cards read `hasPhoto`/`photoRev`, only the photo layer knows where
bytes come from); a `storagePath` field can sit beside `bytes` for a
dual-read release; and backfill is a script, with `key` already on the
document so nothing has to be joined back to `/stock`. Keeping bytes out of
`/stock` protects that exit as well as the quota.

## Test plan

**Pure (JVM), `StockPhotoTest`:** the document id for a catalogue key and a
manual key, and that a display rename does not change it; the long edge capped
at 800; the quality search lands ≤ 81,920 bytes and refuses rather than
exceeding it; EXIF rotation per orientation value; a non-WebP byte sequence
rejected; `hasPhoto: false` reads as "no photo" whatever `photoRev` says.

**Cache, `StockPhotoCacheTest`:** every row of the caching table — a matching
`rev` serves from cache and **issues no read**; a lower cached `rev` fetches
once and then serves from cache; `hasPhoto: false` discards without a read; a
cached entry is never served against a mismatched `rev`; and re-reading an
unchanged photo a hundred times spends one read, not a hundred.

**Write path, `StockPhotoWriteTest`,** against the existing fake store: both
documents written in one transaction with matching `rev`; `q` and `min`
unchanged; `lastAction: "photo"`; **no movement written**; a remove deletes the
photo document and sets `hasPhoto: false` with `photoRev` still advancing; a
replayed transaction body increments `rev` exactly once; and one test per row
of the conflict table — replace vs replace, replace vs remove in both commit
orders, and a photo change racing a quantity change.

**Rules (emulator), `photos.test.js`:**

- a Worker may read a photo document and may not write one; Staff may write;
- 81,920 bytes accepted, 81,921 refused; a non-`bytes` field refused;
- a document carrying a price field refused; `byUid` spoofing refused;
- **a photo document written without the matching `/stock` update refused**;
- **a `/stock` update claiming `hasPhoto: true` with no photo document in the
  same commit refused**;
- **a `rev` that disagrees between the two documents refused**;
- **a `photoRev` that goes backwards refused**;
- **a `/stock` delete that leaves the photo document behind refused**;
- `'photo'` accepted as a `/stock` `lastAction` and refused as a `/stockMoves`
  action;
- a signed-out caller gets nothing.

**Compose (Robolectric):** the source sheet offers exactly two options; the
preview writes nothing until confirmed; cancel writes nothing; a Worker sees a
thumbnail and larger view but no add, replace or remove; offline every control
disabled and says so; a row with `hasPhoto: false` shows no placeholder and
issues no read; a photo that fails to load shows a placeholder, not an endless
spinner.

Of those, `StockPhotoScreenTest` covers the sheets batch D built — two options
and no more, nothing written until confirmed, cancel and "choose another"
writing nothing, a refusal shown and unsavable, offline disabled with the
standard wording, a picture still being prepared unsavable, and a save already
in flight not startable twice. **The thumbnail, the larger view, the Worker
capability gate and the placeholder cases are batch E's** and have no test
yet, because the components they describe do not exist.

## Open decisions

1. **Thumbnail on the card, or an icon?** Thumbnails are assumed, fetched
   lazily. An icon — bytes fetched only when the larger view opens — costs
   almost no reads. Recommendation: thumbnails, with the icon as the fallback
   if T-P14 or the console shows read pressure.
2. **Whether to stagger the first rollout**, so eight devices do not all
   perform their one-off fill on the same day.
3. **Whether archived rows should keep their photos.** The plan keeps them;
   deleting would reclaim capacity at the cost of an irreversible archive.
4. **The quota figures**, to be re-checked against the live page before
   approval.

## When I would recommend postponing photos instead

- If T-P4 shows the quality ceiling does not serve the real items.
- If T-P14 fails and revision-matched caching cannot be made to hold — the
  pathological transfer case then becomes the normal one.
- If the team grows well beyond the eight devices assumed, or the board is
  opened far more often than assumed.

Any of those means the feature wants Cloud Storage, and Cloud Storage means
Blaze. Postponing would then be better than shipping something that degrades
the rest of the app.

## Out of scope for N3.1

Multiple photos per item, photos on products rather than stock rows, photos in
quotations or the PDF, annotation or cropping, barcode scanning, and any
production deployment. Purchase photo attachments belong with N4 if wanted at
all. N3.1 changes no N3 quantity, archive or permission behaviour, and must
not become the reason N3's outstanding device checks slip.
